## 0. Honest premise (what WS-3 is actually for)

WS-1 G1 is **UNDER-POWERED** (N = 7 < N_min = 8). The only Phase-2 mandate is
the 60-day live OJ paper-trading harness (WS-2) that accumulates event-trades to
N ≥ 8 and re-runs G1. The WS-2 blueprint deferred, until the G1 re-run verdict:
*ensemble disagreement, NG, CME HDD/CDD, WS-3 API build, TimescaleDB at scale,
multi-tenancy*. **G2 is infrastructure proof and does not clear G1.**

Therefore WS-3's purpose is:

> A **fast-read API layer** over the WS-2 store that surfaces signals, forecasts,
> data freshness, and (when the ledger permits) honest live performance — serving
> **real, up-to-date data with documented provenance**, never a claim of edge.

An API that serves a signal with no proven edge is premature and, worse, a
liability. So the build is **gated on T0** below. Once the gate clears, WS-3
delivers exactly what Phase 2 needs for trial customers and what Phase 3 needs
for scale — without re-litigating the edge question.

**Edge disclosure is mandatory, not optional:** while G1 is UNDER-POWERED, every
signal/ledger response carries an `X-Pakhi-Edge-Status` header computed from the
ledger (`unproven_n<N>` / `underpowered` / `proven` + `n_scored_events`) so a
consumer can never mistake a data feed for a validated edge.

**Explicitly deferred** to WS-4 (JWT, RBAC, multi-tenancy, audit logs), WS-5
(Prometheus/Grafana, SLOs, status page), WS-6 (metering/billing): only the
**minimum** API-key + rate-limit header layer lands here (T5).

## 1. Purpose

Transition Pakhi from a research tool + batch store into a **credible
single-tenant live service**:

- Workers (WS-2) keep the store fresh; **WS-3 only reads** — no weather model
  runs, no signal evaluation, no backtest execution inside a request.
- Expose the precomputed store: forecast cycles, signals, forecasts, ensemble
  disagreement, data freshness, and the paper-ledger state.
- Autogenerated OpenAPI docs; `/v1` versioning; rate-limit headers; structured
  logs + request IDs; WebSocket push on each new model cycle.
- Ship the **`pakhi.client`** SDK (thin, typed) **inside this repository** — no
  separate PyPI package in Phase 2 (`from pakhi.client import PakhiClient`).
- Deploy as a single Docker image extending the existing `Dockerfile`.

Success = a live, documented, versioned API serving **real, up-to-date,
provenance-complete data** with a defined freshness contract — and a WebSocket
push that fires when the WS-2 cycle lands.

## 3. Architecture & Data Model

**The Precompute Principle (unchanged from WS-2):** no weather model is run and
no signal is evaluated during an API request. WS-3 is a thin, read-only-by-
default service over the store.

```
┌──────────────┐    ┌──────────────┐    ┌───────────────────────┐
│ ws2 systemd  │──▶│ Postgres     │◀───│ WS-3 FastAPI          │
│ / GH Actions │   │ (single      │    │  read_engine (GETs)   │
│  ingest→compute│  │  source of   │──▶│  write_engine (POST   │
│  ...UPSERT... │   │  truth)      │NOTIFY│  backtests)         │
│  NOTIFY ✔     │   └──────────────┘    │  WS /v1/stream/*     │
└──────────────┘       LISTEN ⬆          └───────────┬───────────┘
                                                      │  pakhi.client
```

### 3.1 Two DB engines — read and write are separate, by role

The API needs **two** SQLAlchemy engines (never one "read-only API engine"):

- **`read_engine`** — `postgres_readonly` role (`SELECT` on all store tables).
  Used by every `GET /v1/*` data query.
- **`write_engine`** — the app role (same as WS-2 workers). Used **only** for the
  two mutations WS-3 is allowed: `INSERT` into `backtest_jobs`
  (`POST /v1/backtests`) and API-key/rate-limit bookkeeping (T5). No other write
  path exists; provenance tables (`signals`, `forecast_cycles`, `paper_ledger`,
  `metrics`) are **write-locked to the workers**.

Both are sync SQLAlchemy 2.0 engines (psycopg2-binary, the `postgres` extra).
Engines are pooled independently; a `postgres_readonly` privilege error in a GET
is a config bug that fails loudly in CI (permission test), never a silent 500.

### 3.2 Freshness contract

`GET /v1/status` reports the latest ingested cycle, its `publication_ts`, and
staleness (now − publication_ts). The pipeline's **never-empty / never-silent-drop**
rule means "no cycle today" is a visible *stale* state with the last-known data +
an `X-Pakhi-Staleness` header — never a fabricated "fresh" value.

### 3.3 Versioning & rate limiting

All routes under `/v1`. Breaking schema changes bump the major version.
`X-Pakhi-Version` on every response. Token-bucket per API key;
`X-RateLimit-Limit` / `-Remaining` / `-Reset` on every response (WS-4 minimum;
keys hashed at rest via `sha256`).

### 3.4 Event-loop policy (mandatory, decided in T1)

**Default = Option A:** all read/write *data* endpoints are declared as
**synchronous `def`** handlers. FastAPI runs them in its anyio worker threadpool,
so the asyncio loop stays free for WebSockets. **WebSocket endpoints are the only
`async def` handlers.** Add a lint/test guard: a test asserts no `async def`
endpoint performs blocking DB work (i.e., handlers that touch `engine` are `def`).

**Option B (allowed alternative):** pure-async with `psycopg[binary]` (v3) or
`asyncpg` + `create_async_engine`/`AsyncSession` added to the `api` extra. If B is
chosen it is used **for everything**, including the NOTIFY listener — no mixing.

### 3.5 WebSocket push — Postgres LISTEN/NOTIFY, not an in-process broker

`run_ws2_t3_orchestrate.py` is a **separate batch process** (systemd timer / GH
Actions cron); uvicorn is another OS process with its own memory. **No in-process
pub-sub broker can receive the worker's events** — that earlier draft claim was
wrong. The bridge is the database:

1. After the ledger UPSERT commits, `orchestrate.py` executes
   `NOTIFY cycle_complete, '{"cycle_id": "20260813_12z"}'` on the **same**
   Postgres connection (payload = JSON: `cycle_id`, `publication_ts`). NOTIFY is
   transactional-safe: it only fires on commit, so a rolled-back cycle never
   pushes.
2. uvicorn opens a **dedicated** `LISTEN cycle_complete` connection at startup.
   Because psycopg2 is sync, the listener runs in a **background thread** that
   blocks on `conn.notifies()` and dispatches each notification to the loop via
   `loop.call_soon_threadsafe` → an `asyncio.Queue`.
3. A single consumer task fans the queue item out to all connected
   `WS /v1/stream/signals` clients (contract schema from T0). Missed subscribers
   are covered by the `GET /v1/signals` history — NOTIFY is a wake-up, not the
   source of truth.

Single-instance footprint, **zero extra services**; graduation to Redis
Pub/Sub/Streams is documented only as a multi-instance (WS-5) path.

### 3.6 Backtest-as-a-service (write path)

`POST /v1/backtests` **validates + enqueues only** (via `write_engine`); the
worker process executes jobs and writes results to a shared artifact store.
`GET /v1/backtests/{id}` returns status; `GET /v1/backtests/{id}/result` streams
the artifact. Workers, never the API, execute backtests.

## 4. Tasks, sequencing, exit criteria

### T0 — Gate decision + API contract skeleton
Before **any** endpoint ships:
- Record the gate verdict in `docs/WS3_PROGRESS.md`: **G1 re-run PASS** (cite the
  self-hash-pinned G1 report on the live ledger) **or** an explicit user infra-first
  decision. If the ledger is UNDER-POWERED at 60 days, WS-3 stays gated and the
  blueprint is *prepared, not executed* — the honest state.
- Freeze the **API contract** first: `docs/WS3_API_CONTRACT.md` + machine twin
  `data/ws3/api_contract.json` (hash-pinned). Lock: route table, request/response
  schemas, error envelope (`{error: {code, message, details?}}`), rate-limit
  headers, freshness semantics, WebSocket message schema, versioning policy,
  `X-Pakhi-Edge-Status` computation, and the **backtest param bounds**:
  `max_window_days <= 365`, whitelisted `model_version` values, and per-key cap
  (1 queued backtest / 5 min).
- Add `pakhi.api` package skeleton + extras:
  `api = ["fastapi>=0.110", "uvicorn[standard]>=0.29", "pydantic>=2.0",
  "websockets>=12.0", "httpx>=0.27"]` (**not** in `[all]`).
- **Exit:** contract doc + machine JSON approved and hash-pinned; gate verdict
  recorded; empty `pakhi/api/` package imports cleanly.

### T1 — FastAPI app, health/status, OpenAPI (week 1 of build)
- `pakhi/api/main.py` (lifespan-managed). **Endpoint policy locked (§3.4):**
  data handlers are sync `def`; only WebSockets are `async def`.
- **Two engines (§3.1):** `pakhi/api/db.py` builds `read_engine` and
  `write_engine` from env (`PAKHI_DB_READ_URL`, `PAKHI_DB_WRITE_URL`).
- `GET /v1/health` — **liveness only** (process + framework up → `{"status":"ok"}`;
  503 on fatal startup failure). For Docker/K8s probes.
- `GET /v1/status` — **readiness + data freshness**: DB reachability, latest
  cycle id + `publication_ts`, staleness, worker last-run (from `metrics`).
- **CORS:** `CORSMiddleware` configured in T1 (allowlist via env; needed by any
  browser dashboard).
- **Uniform error envelope:** custom `RequestValidationError` and `HTTPException`
  handlers convert FastAPI's default `{detail: [...]}` into the locked
  `{error: {code, message, details?}}` schema — including 422s.
- Structured logging (JSON lines, request id middleware), request-id propagation.
- **Exit:** health/status live; a known-stale DB shows honest stale state; a
  422 and a 404 both return the locked envelope; CORS preflight passes; logs are
  JSON with request ids; the "no async DB in handlers" guard test exists.

### T2 — Read endpoints (week 1–2)
- `GET /v1/instruments` — distinct instruments with latest signal + freshness.
- `GET /v1/signals/{instrument}` — latest + history (`?limit`, `?since`,
  `?cycle_id`); **provenance columns surfaced verbatim**; empty ⇒ 404, never an
  empty 200 body. Response carries `X-Pakhi-Edge-Status`.
- `GET /v1/forecasts/{instrument}?lead=7d` — stored forecast rows (not computed).
- `GET /v1/ensemble/disagreement` — stored disagreement series; if deferred from
  WS-2, returns 501 with the honest "not yet computed" contract message.
- `GET /v1/ledger` — paper-ledger summary (count, scored events, net) from the
  `paper_ledger` rows, clearly labeled *paper / not live capital*, with
  `X-Pakhi-Edge-Status`.
- **Exit:** every endpoint covered by pytest `TestClient` tests asserting
  schema, provenance passthrough, 404-vs-200 semantics, and edge-status header;
  a fixture DB with 3 cycles reproduces exact responses.

### T3 — Backtest-as-a-service job queue (week 2–3)
- `backtest_jobs` table (`id`, `status`, `params JSON`, `result_url`,
  `created_at`, `finished_at`); created by a migration run as the **app role**.
- `POST /v1/backtests` (**via `write_engine`**) validates against the locked
  bounds → enqueues (INSERT). `GET /v1/backtests/{id}` → status;
  `GET /v1/backtests/{id}/result` → artifact stream.
- **Worker:** separate process (dedicated systemd timer / extended
  `ws2-orchestrate` unit), picks up `queued` rows, executes with the exact WS-1
  evaluation semantics (never a loose re-implementation), writes results to a
  shared artifact store (`data/ws3/backtests/` on the worker host; API serves it
  read-only via the same mounted volume in the single-instance deploy).
- **Exit:** queued job transitions `queued→running→done`; a `failed` job returns
  the error envelope; result endpoint streams the artifact; param-bound rejection
  (window > 365 d, unknown model, queue-full) returns 422/429 with the locked
  envelope; the API process is never blocked by job execution.

### T4 — WebSocket live stream (week 3)
- `WS /v1/stream/signals` — **only `async def` endpoint**; heartbeat ping;
  `X-Pakhi-Version` framing.
- **Bridge per §3.5:** `orchestrate.py` runs `NOTIFY cycle_complete` after the
  ledger UPSERT; uvicorn's dedicated LISTEN connection (background thread →
  `asyncio.Queue` → fan-out). LISTEN connection failure is logged + re-established
  with backoff; a missed NOTIFY is never a data loss (history covers it).
- **Exit:** a running uvicorn pushes a signal frame within the staleness target of
  a cycle completing in a test double (real Postgres + real NOTIFY); disconnect/
  reconnect is clean; the "rollback never pushes" case is tested.

### T5 — API keys, rate limiting, `pakhi.client` SDK (week 3–4)
- **Key storage:** keys come from `PAKHI_API_KEYS` env (comma-separated) or
  `data/ws3/api_keys.json`; stored **hashed** (`sha256`); checked against the
  hash on every request (`X-Pakhi-Key`). No DB round-trip per request at
  Phase-2 scale.
- **Rate limiting:** token-bucket state **in-memory** (thread-safe dict). The
  contract **documented as single-worker**: `uvicorn --workers 1` (or `1` uvicorn
  process); running multiple workers would split bucket state — explicit
  non-goal until WS-5/Redis.
- **SDK layout:** `pakhi.client` inside this repo (`pakhi/client.py`), exported
  as `from pakhi.client import PakhiClient` → `.status()`, `.signals(instrument)`,
  `.forecasts(instrument)`, `.ledger()`, `.backtests.create()`,
  `.stream_signals(on_signal=...)`; docstrings link to OpenAPI.
- **Exit:** SDK round-trips against the running API in integration tests;
  exceeded rate limit returns 429 with correct headers; unknown key → 401;
  hashes (never plaintext keys) in the store file.

### T6 — Deployment + CI/CD + integration tests (week 4)
- Extend `Dockerfile` with an `api` service entrypoint (`uvicorn pakhi.api.main:app`),
  still single image (tag/env selects `api` vs `ws2` command), non-root, healthcheck
  on `/v1/health`.
- `.github/workflows/ws3-api.yml` (or extend `ci.yml`): build, run API integration
  tests against a Postgres 16 service container (with both roles provisioned),
  push image on green.
- `docker-compose.yml` gains an `api` service wired to the same Postgres.
- **Exit:** green integration suite in CI (contract tests over real store);
  container healthcheck passes; deploy docs in `docs/WS3_DEPLOY.md`.

## 5. Rules & Discipline (applies to all tasks)

1. **Fast-read only.** No weather fetch, model run, or signal evaluation in a
   request. The store is the single source of truth; workers write, API reads.
2. **Never return an empty DataFrame / empty 200.** Missing data ⇒ 404 or the
   explicit stale-state contract — never a silent empty success.
3. **Provenance passthrough.** `forecast_cycle_id`, `publication_ts`,
   `archive_source`, `model_version` (and `vintage_hash`/`fetch_date` on the
   ledger) are surfaced verbatim in API responses.
4. **Honesty over freshness.** A stale cycle is labeled stale (`X-Pakhi-Staleness`,
   `status.freshness = "stale"`), never backfilled or implied current. Edge status
   is always disclosed (`X-Pakhi-Edge-Status`), computed from the ledger.
5. **Contract-first.** Every endpoint ships with its contract entry and an
   OpenAPI schema before code review; any change re-locks the pinned contract.
6. **Rate-limit + key discipline from day one** (T1 headers, T5 enforcement) —
   retrofitting auth/limits is how public APIs rot.
7. **Roles are enforced, not assumed.** A GET path that uses `write_engine`, or a
   write that uses `read_engine`, fails a CI permission test. Postgres privileges,
   not app discipline, protect the provenance tables.

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| **Building a public API before the edge is proven** | T0 gate hard-blocked on G1 verdict / explicit infra-first decision; `X-Pakhi-Edge-Status` on every signal/ledger response |
| **Worker cycle events can't reach the API** (IPC) | Postgres LISTEN/NOTIFY bridge (§3.5); NOTIFY is transactional; history endpoints cover missed pushes |
| **API reads drift from worker-written semantics** | Provenance passthrough + contract tests against a fixture store in T2; stored-vs-API equivalence gate |
| **Stale data presented as fresh** | Freshness contract (§3.2) + `X-Pakhi-Staleness` header + test for known-stale DB |
| **Blocking DB calls freeze WebSockets** | Sync `def` handlers + anyio threadpool (§3.4); guard test bans async DB work; WebSockets stay async |
| **Read-only role blocks the one legit write** | Two engines (§3.1): `write_engine` scoped to `backtest_jobs` + key metadata only; CI permission test |
| **Backtest queue starves the host** | Locked param bounds + per-key cap (§3.6/T0); jobs run in the worker process only |
| **Rate-limit state splits across workers** | Documented single-worker deployment; multi-worker is an explicit WS-5 (Redis) goal |
| **Browser clients blocked by CORS / non-standard errors** | CORSMiddleware + custom 422/HTTPException handlers to the locked envelope (T1) |
| **psycopg2-style teardown crashes in the API image** | `api` extra separate from base/`all`; API ships with the same `[all,postgres]` install the workers use — any teardown issue is caught by the CI integration job before ship |

## 8. Handoff to WS-4 / WS-5

WS-3 delivers a documented, versioned, single-tenant fast-read API with keys,
rate limits, and a NOTIFY-bridged live stream. **WS-4** adds JWT + RBAC +
multi-tenancy + audit logs and begins the SOC2 controls program (Phase 3 starts
week 16). **WS-5** adds Prometheus/Grafana metrics, SLOs (API 99.9%, signal
within 60 s of cycle publication, staleness < 1 cycle), a public status page,
multi-worker rate limiting (Redis), and DR/backups. WS-6 (metering/billing)
builds on WS-4's per-key accounting and WS-3's rate-limit headers. Nothing in
WS-3 pre-commits to tenancy, billing, or compliance claims.
